# tools/business

业务工具。这是三层分类中数量最大、差异最大的一类，也是 `Tool Search` 和 `Tool Exec` 的主要作用对象。

## 判定标准

一个工具放进这个目录，需要满足以下条件之一：

- **发现成本高（\(\kappa\) 高）。** 模型仅凭名称和简短描述难以可靠定位。典型信号是名称包含版本号、缩写、内部前缀（如 `biz_order_center_refund_v3`），或者同名工具在不同租户下语义不同。
- **有副作用或外部状态依赖。** 调用会改变持久状态，或者结果依赖于工具库之外、不受本系统控制的系统状态。即使逻辑只有一行代码、schema 只有两个字段，也属于这一类。
- **属性组合不满足基础工具或 capability 工具的判定条件。**

前两类并不互斥。一个只读的天气查询工具（\(\kappa\) 高、无副作用）和一个有副作用的退款工具（\(\kappa\) 高、有副作用）都在这个目录里。搜索的必要性来自发现成本，执行准入的必要性来自副作用和外部依赖，两者解耦。

## 规模与检索瓶颈

这个目录的规模是压倒性的。如果工具库有一万个工具，基础工具和 capability 工具加起来通常不超过几十个，剩下约 99.5% 都在这里。

规模带来的第一个后果是**检索成为主导瓶颈**。LiveMCPBench 在 10,000+ MCP server 的设置下评测 12 个模型，发现检索错误占全部失败案例的近一半，远超模型自身选择错误的比例[reference:0][reference:1]。这意味着 `Tool Search` 的设计质量直接决定了业务工具能否被用起来，模型“会不会调用工具”在这个规模上已经退居次要位置。

第二个后果是**上下文预算的约束在注册阶段就应当被考虑**。单个业务工具的 schema 平均 100–270 tokens，一万个工具的 schema 总量在 100 万到 270 万 tokens 之间。这个数量不可能被任何上下文窗口容纳，因此业务工具不进入模型的初始可见集合，只通过 `Tool Search` 按需披露。

## 工具文档的质量问题

检索质量的上限由被检索的文本决定。MCP 生态的现状是：官方参考 server 的输入 schema 中，大量参数字段缺少 `description`，模型只能从字段名猜测含义。工具名称的规范程度也参差不齐——snake_case 是多数公共 server 的惯例，但版本号、缩写、内部前缀仍然普遍存在，同一语义在不同 server 下可能对应完全不同的名称。

Tool-REX（ICLR 2026）的工作把这个问题定位为工具检索的首要瓶颈：原始工具文档缺少“何时使用”“有什么限制”“典型输入输出”这些对检索至关重要的字段，用一条低成本的 LLM 流水线把文档扩展成结构化 profile（`function_description`、`when_to_use`、`limitations`、`tags`）之后，检索性能有实质性提升[reference:4]。

这个目录的 README 不规定检索器的实现，但要求一个前置条件：**业务工具在注册时应该提供一份面向检索的档案**，而不是只依赖原始 `description`。档案至少包含场景标签、扩展后的使用条件描述、以及从参数 schema 或实现体提炼的检索摘要。`ToolRegistry` 索引的是这份档案，模型最终看到的仍然是精简 schema。两者分离，既保召回，又不撑爆上下文。

## 多租户与命名隔离

业务工具的数量在单租户下已经很大，在多租户系统里还会进一步膨胀。如果不同租户的工具全部混在一个命名空间里，检索时即使场景硬过滤能排除无权访问的工具，名称碰撞和语义碰撞仍然可能发生在有权访问的工具之间——租户 A 的 `refund` 和租户 B 的 `refund` 可能含义完全不同。

常见做法是每个租户持有独立的工具注册表，租户之间的工具互相不可见[reference:5]。在这个目录的上下文中，这意味着 `Tool Search` 的硬过滤阶段必须携带租户标识，检索的候选宇宙在评分之前就已经被限制在当前租户的工具集合内。硬过滤是安全边界，不能交给 reranker 去做。

## 与 search 和 exec 的分工

`Tool Search` 负责**发现**：在业务工具的候选宇宙上，通过场景硬过滤、关键词快速通道和 BM25 + 向量融合召回，把候选集从一万压到模型能看见的 \(k\)。返回的是带置信度信号的 schema 候选包，无匹配时返回明确的 `NO_MATCH`，不强行凑数。

`Tool Exec` 负责**准入**：模型从候选中选定工具、给出参数之后，网关在 handler 之前完成鉴权、幂等检查和错误分类。可见不等于有权执行，模型不能通过参数绕过权限边界；写操作必须携带从业务键派生的幂等键；超时在写操作上被当作“结果未知”处理，先确认后置条件再决定是否重试。

两者之间的接口是第 3 章定义的候选包和第 4 章定义的执行结果结构。这个目录不规定 `Tool Search` 和 `Tool Exec` 的内部实现，只规定业务工具对它们提出的要求：**发现需要一份可检索的档案，执行需要结构化的错误和幂等语义**。

## 工具的编写约定

**每个业务工具必须携带 `readOnlyHint` 和 `scene` 元数据。** `readOnlyHint` 决定 `Tool Exec` 是否触发写操作确认和幂等检查；`scene` 是 `Tool Search` 硬过滤的依据。缺少这两个字段的工具会在网关层被拒绝注册，而不是在运行时被猜测。

**工具描述写明“不做什么”。** 两个相似工具（如 `query_order` 和 `query_order_history`）的描述应该互相指出区别，而不是各自只描述自己。MCP 工具质量检查中有一条明确的判据：当两个工具重叠时，每个描述应该说明何时使用另一个[reference:6]。业务工具的数量决定了相似工具混淆是高发错误，这一条对降低错误调用率有直接效果。

**错误返回结构化类别。** 工具实现内部对可预期的业务失败返回带 `category` 的错误（`param`、`business`、`auth`、`transient`、`protocol`），而不是裸的异常消息。网关依赖这个类别决定是否重试、是否回到模型修正参数、还是直接终止。没有类别的错误在网关层被归入 `protocol`，这是最保守的默认值。
