# tools/capability

可选能力工具。这里的工具是否对模型可见，由宿主环境在会话级别控制，不经过 `Tool Search` 的检索管道，也不由模型通过搜索自行发现。

## 判定标准

一个工具放进这个目录，需要同时满足两条：

1. **代表一种通用能力。** 这一条把“访问互联网”和“查询深圳天气”区分开：前者是会话级能力，由宿主决定开不开；后者是绑定具体业务语义的动作，由检索去发现。
2. **可见性由宿主显式配置决定。** 用户在页面上勾选“允许联网”，或者在会话配置中打开某项能力，对应工具才进入模型的可用集合；未打开时，它们对模型不可见，也不出现在检索候选宇宙里。

这两条把 capability 和 business 区分开：business 工具的规模决定了必须靠检索发现，capability 工具的数量很小，靠配置开关控制更直接。

## 网络访问能力

### 能力边界

`web_search` 和 `web_fetch` 共同构成“访问互联网”这一项能力。宿主打开这项能力时，两个工具一起注入；关闭时，两个都不可见。不提供“只开搜索不开抓取”的细粒度配置，因为搜索结果通常需要进一步抓取才能得到完整信息，只开一半会让模型频繁走到“搜到了但读不了”的死路。

### `web_search`

输入一个查询字符串，返回搜索结果列表，每条包含标题、URL 和摘要。摘要由搜索后端提供，长度可控，不包含完整页面内容——完整内容需要 `web_fetch` 去取。

搜索后端的可替换性是这一层的设计重点。具体使用哪个搜索引擎（自建、商业 API、内部检索服务）不影响工具对模型的接口，也不影响 `web_fetch` 的配合方式。

### `web_fetch`

输入一个 URL，返回该页面的正文内容，以 Markdown 或纯文本形式给出。不返回原始 HTML。

这条约束的理由是上下文成本。一个典型网页的原始 HTML 包含导航栏、脚本、样式、广告，正文往往只占其中很小一部分；把整页 HTML 回灌给模型，既浪费 token，也让模型难以定位有效信息。正文提取的质量比抓取本身更重要。正文提取失败时返回明确的 `ERROR`；退化为返回原始 HTML 会让调用方误以为拿到的是可用内容。

`web_fetch` 只做只读抓取，不执行页面脚本，不维持登录态，不跟随需要交互的重定向。需要这些行为的场景属于浏览器自动化能力，不属于这里。
